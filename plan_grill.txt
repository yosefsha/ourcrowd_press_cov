  Q2: When does a news item count as a Mention?

  The News Source returns candidates. Searching "Harvey" gives you Harvey
  Weinstein and Hurricane Harvey. "Wave" and "Ro" are worse. Even "Island" (the
  enterprise browser company) is drowned out by travel news. If we store
  everything the search returns, the dashboard is wrong for at least 30–40 of
  the 258 companies.

  The question splits into two parts:

  (a) Where does the disambiguating context come from? The seed list is names
  only. I recommend we keep ourcrowd_companies.txt as the source of truth for
  who is tracked, and add a curated companies.json next to it that enriches each
  entry with optional aliases (including the "formerly X" names), domain, a
  one-line description/sector, and searchTerms. Only the ambiguous names need
  search terms. Example: Harvey becomes "Harvey" AI legal. An entry with no
  enrichment falls back to its quoted name. A startup check fails loudly if
  companies.json names a company that isn't in the seed list.

  (b) Who makes the final call? I recommend that Ollama decides relevance in the
  same call as sentiment. The prompt gets the company's name, aliases and
  description plus the article title and snippet. It returns { relevant: 
  boolean, sentiment, reason }. An irrelevant item is kept but marked rejected,
  not dropped. That gives an audit trail for the "how did you validate quality"
  section of the README. It also stops the daily job from re-classifying the
  same irrelevant article every day.

  So, proposed definitions:
  - Candidate: any item a News Source returns for a Tracked Company.
  - Mention: a candidate the classifier confirmed is about that Tracked Company.
    Only Mentions appear on the dashboard, count toward the "last mentioned"
    status, and trigger alerts.

  Do you agree with both parts? In particular, are you OK with hand-curating
  search terms for the ambiguous names, or do you want something more automatic,
  such as having the LLM generate the descriptions once?

  Q4: What exactly triggers an alert, and where does it go?

  There are four sub-decisions. Here's my recommendation for each.

  (a) What does "new" mean? A Mention is new if it was first seen in this Daily
  Check. Its publication date doesn't decide that. Google News often surfaces an
  article a day or two after it's published, and a rule based on publication
  date would miss those. There is one guard: a Mention first seen today but
  published more than 7 days ago is stored and shown on the dashboard, but it
  doesn't trigger an alert, because by then it isn't news.

  (b) What about the Backfill? It never alerts. Otherwise the first run would
  send thousands of "new" Mentions.

  (c) One alert per Mention, or one digest per run? I recommend one digest per 
  Daily Check, grouped by company, with negative Mentions listed first. That's
  what a portfolio manager wants to read each morning. SpaceX alone could
  produce 20 Mentions a day, and a separate message for each would bury the one
  negative story about a small company. If a run finds no new Mentions, it sends
  no alert and just logs "no new mentions".

  (d) Which channel? An AlertNotifier interface with two implementations, both
  justified by the brief:
  - Always: write the digest to the log and to data/alerts/<date>.json. That's
    visible with no setup, and it lands in the data/ folder the reviewers asked
    for.
  - When SLACK_WEBHOOK_URL is set: post the digest to Slack as well. That's the
    realistic production channel, and an incoming webhook needs no OAuth app.

  Email would need SMTP credentials and is harder for a reviewer to verify, so
  I'd leave it out.

  Do you agree with all four, especially the 7-day staleness guard and
  digest-per-run? Or do you want something like an immediate alert for negative
  Mentions?

  Q9: How should a one- or few-command local run work?

  Wrapping it in npm is the right idea. I'd adjust two things about it,
  explained below.

  Option A: root package.json with npm scripts only. For example, "start": 
  "ollama serve & docker compose up --build".
  - ✅ Familiar to a Node reviewer and needs no extra tooling.
  - ❌ npm scripts are one-line shell commands. They can't check prerequisites
    properly, and they behave differently on zsh, bash and Windows cmd.
  - ❌ ollama serve & leaves an orphaned background process. If the Ollama macOS
    app is already running (it starts at login), ollama serve fails because the
    port is already in use.
  - ❌ When something fails, the error is cryptic ("connection refused" from
    deep in the backend) instead of "Ollama isn't installed, run brew install 
    ollama".

  Option B (my recommendation): root package.json whose scripts call small Node 
  scripts.
  npm run setup    # check Docker, Node ≥22 and Ollama; pull qwen2.5:7b if 
  missing; npm ci in both apps
  npm start        # make sure Ollama is serving (start it only if it isn't); 
  docker compose up --build:
                   #   postgres → migrate (one-off) → backend → frontend; print 
  the dashboard URL
  npm run backfill -- --until=3d   # optional CLI path; the dashboard has the 
  same control
  npm stop         # docker compose down (leaves Ollama alone, since it may be 
  shared)
  - ✅ Two commands from clone to dashboard. Each failed check prints the exact
    fix.
  - ✅ Written in Node .mjs scripts, so it fits the "JavaScript (Node.js)"
    requirement and works on macOS, Linux and Windows.
  - ✅ npm start is safe to run repeatedly. It never starts a second Ollama.
  - ❌ It's a small amount of extra code (~100 lines) to maintain.
  - ❌ It won't install Ollama itself. That's a system-level install (brew or a

  it's 6–8 manual commands, and any one of them can be missed. That's exactly

❯ i want to use session cookie with SameSite=Strict setting                     
  is it possible with separate frontend container with /api proxy . ?           

⏺ Yes. The /api proxy is what makes it work cleanly.

  Why it works: the browser only ever talks to the frontend's origin, say
  http://localhost:8080. When the backend replies with Set-Cookie through the
  proxy, the browser stores the cookie for that origin, because it can't tell a
  proxy is involved. Every later /api/... request is same-origin and same-site,
  so a SameSite=Strict cookie is sent. The Vite dev proxy behaves the same way.

  Settings to get right:
  - Don't set a Domain attribute, and use Path=/. The cookie is then scoped to
    exactly the host the browser sees. If Domain were set to the backend's own
    hostname, the browser would reject the cookie.
  - The proxy must pass Set-Cookie through unchanged. Both nginx and Vite's
    proxy do this by default. Just don't add cookie-rewriting directives.
  - Use HttpOnly always, and Secure whenever the site is served over https.
    Chrome and Firefox treat http://localhost as secure, so Secure cookies work
    there. Older Safari versions don't, so a local run over plain http needs
    Secure controlled by config, with a production default of on.
  - Nest needs app.set('trust proxy', 1). It then reads X-Forwarded-Proto and
    X-Forwarded-For from the proxy and correctly detects https.
  - SameSite=Strict mostly closes off cross-site request forgery (CSRF), but it
    isn't a complete defence on its own. I'd also reject state-changing requests
    (POST /checks, Backfill, acknowledging a digest) whose Origin header
    doesn't match. That's one small guard.

  (Without a proxy it would still technically work. localhost:5173 and
  localhost:8000 count as the same site, because ports don't matter for
  SameSite. But you'd need CORS with credentials, and that falls apart as soon
  as the frontend and backend are on different domains. The proxy avoids all of
  that.)

  Q11: Can a full Backfill finish on this laptop?

  Here's a rough estimate:
  - Candidates: about 40 heavily covered companies hit Google's cap of ~100
    each, and the long tail averages maybe 10–20. That's roughly 8,000–12,000 
    Candidates.
  - Cost per call with qwen2.5:7b on an M3: reading the prompt is fast, but
    generating a JSON verdict with a reason runs at about 20 tokens/second.
    That's roughly 1.5–2.5 s per call.
  - Total: 10,000 relevance calls plus sentiment on the Mentions comes to about 
    6–9 hours. A reviewer can't wait that long, and it makes every iteration
    during development painful.

  I recommend four measures together:

  1. A free check before calling the LLM. If neither the company's name nor any
     alias appears in a Candidate's title or snippet, reject it right away with
     the reason "name not present", and skip the LLM. Google search does return
     items like that, especially for multi-word names. This doesn't replace the
     LLM's relevance check; it just avoids wasting calls.
  2. Cap each company at the 50 most recent Candidates per Backfill. Companies
     at that level are already sampled because of Google's 100-item cap. The
     dashboard labels them "50+" so the cap is visible and not mistaken for a
     full count. The Daily Check isn't capped, because it only sees about a
     day's worth of items.
  3. Run the Backfill in the background and make it resumable. It works through
     one company at a time and saves results as it goes. The dashboard shows
     progress (for example "112 / 258 companies") and fills in live. If it's
     interrupted, re-running skips Candidates it has already classified, because
     deduplication by URL handles that.
  4. Keep LLM output short and allow slight parallelism. The reason is capped at
     about 15 words, since output tokens are what cost time, and up to 2
     requests are sent to Ollama at once (OLLAMA_NUM_PARALLEL). Both are
     configurable.

  Together I'd expect roughly 1.5–3 hours for a full Backfill, and the dashboard

  Q12: What makes two Candidates "the same article"?

  De-duplication decides what counts as one Mention, the "first seen" rule for
  alerts, and whether a re-run classifies something again. Three real
  situations:

  (a) One article mentions two Tracked Companies. "Anthropic and xAI raise 
  record rounds" appears in both companies' search results.
  My recommendation: it's one article but two Mentions, one per company, each
  with its own Relevance Verdict and Sentiment. The verdicts can differ: the
  article might be positive for Anthropic and negative for xAI. Since Sentiment
  is defined toward the company, a Mention's identity has to be (article, 
  company).

  (b) The same story in several outlets. A Reuters piece republished by 30
  sites, or a press release picked up widely.
  My recommendation: count each outlet as a separate Mention. Investor-relations
  people do count outlets ("covered in 30 publications"), and every link really
  is a separate appearance. The dashboard can show the outlet name next to each
  one. Grouping syndicated copies would need fuzzy title matching, which is a
  backlog item, not version 1.

  (c) Which URL identifies the article: a real implementation risk. Google News
  RSS links look like news.google.com/rss/articles/CBMi.... Since 2024 these
  can't be resolved by following an HTTP redirect: the browser follows a
  JavaScript redirect, and resolving them from a server means calling an
  undocumented internal Google endpoint, which is fragile and may be
  rate-limited.
  My recommendation:
  - Identity key = the Google article ID (the CBMi… token). It's stable for each
    article and always available.
  - Try to resolve the real publisher URL, best effort. On success, store it and
    link to it. On failure, store the Google link, which still opens the
    article in a browser. Every Mention therefore links back to its source, as
    the brief requires.
  - Store the outlet's name and homepage from the RSS <source> element either
    way.
  - The README says this plainly. When a second News Source arrives,
    de-duplication across sources would need the resolved URL, which is a
    backlog concern.

  Do you agree with all three: Mention = (article, company); syndicated copies
  counted separately; Google article ID as the identity, with the publisher URL
  resolved best effort?

  Q14: How do runs behave: scheduling, overlapping runs and failures?

  A Backfill and a Daily Check are both a Run. Here's what I propose for how
  they behave:

  (a) Scheduling. A cron inside the backend (@nestjs/schedule), daily at 07:00 
  Asia/Jerusalem, configurable through DAILY_CHECK_CRON and TZ, so the digest is
  waiting at the start of the day.
  - Catching up: a laptop is often asleep at 07:00. When the backend starts, if
    the last successful Daily Check is more than 24 hours old, it runs one
    immediately.
  - "Since the previous run" = from the start of the last successful Daily Check
    minus 1 day of overlap. The overlap costs nothing, because duplicates are
    dropped and already-classified Articles aren't classified again, and it
    catches Articles Google surfaced late.

  (b) Only one Run at a time. A Backfill and a Daily Check never overlap. They'd
  duplicate work and compete for Ollama. A lock in the database (at most one
  Run with status running) enforces this, and starting another returns 409 
  Conflict with "Backfill in progress, 112/258". The dashboard greys out the
  buttons while a Run is going.

  (c) Failures.
  - Fetching fails for one company: record the error against that company and
    carry on with the rest. The Run ends as completed_with_errors and the
    operations panel lists which companies failed.
  - Ollama fails: after 5 consecutive classification failures, Ollama is treated
    as down and the Run stops as failed. Fetched Candidates are stored 
    unclassified and picked up by the next Run, because classification is a
    separate step that can be retried.
  - Crash or restart mid-Run: on startup, any Run still marked running is
    changed to interrupted. Starting again resumes it, because work already done
    is skipped.

  (d) One correction to "New Mention". Take an Article fetched in Monday's run
  that couldn't be classified because Ollama was down, then classified as
  relevant on Tuesday. Under "first seen" it would never alert. The definition
  becomes "first confirmed as a Mention in this Daily Check, and published 
  within the last 7 days". Stated that way, failures can't swallow alerts.

  Do you agree with all four, including 07:00 Asia/Jerusalem, the 5-failure
  threshold, and the corrected New Mention definition?

  Q16: How do we separate the collector from the API server?

  Proposal: one backend codebase with two entry points, built into the same 
  image and run as separate processes.

  backend/src/
    main.ts            → API server: HTTP only. Never fetches news or calls 
  Ollama.
    worker.ts          → Collector: a Nest app with no HTTP. Runs Backfills and 
  Daily Checks, owns the cron.
    coverage/ runs/ alerts/ ...   shared domain modules; each entry point 
  imports only what it needs
  - In docker-compose.yml the same image is used twice: api runs node 
    dist/main.js, and collector runs node dist/worker.js.
  - The API module graph never imports the NewsSource or classifier modules. A
    lint rule enforces that boundary, so the separation can't quietly erode.

  How they communicate: through Postgres, using the Runs table as the queue.
  1. The dashboard calls POST /api/runs {type: "backfill", until, companies}.
     The API inserts a Run with status queued and returns 202 Accepted. The
     one-Run rule becomes "at most one Run that is queued or running", enforced
     by a partial unique index, and a conflict returns 409.
  2. The collector checks for queued Runs every few seconds. It claims one with
     SELECT … FOR UPDATE SKIP LOCKED, runs it, and writes progress to the Run
     row.
  3. The dashboard keeps polling the API, which reads progress from that row.
  4. The cron inside the collector does the same thing: it inserts a queued
     Daily Check.

  Why this approach:
  - No new infrastructure. We already need a Runs table for the lock, progress
    and history, so making it the queue costs almost nothing. The repo rules say
    not to add a service CI doesn't need. Redis with BullMQ would mean a Redis
    container plus CI changes for a queue that only ever holds one job.
  - Each process fails on its own. If Ollama is down, the collector fails while
    the API keeps serving the dashboard. That also refines ADR-007: only the 
    collector refuses to start without Ollama. The collector writes a heartbeat
    row with its Ollama health, and the dashboard shows "Collector offline" or
    "Ollama unreachable" instead of an API error.
  - The production path is clear. The collector becomes its own ECS service, or
    EventBridge can launch it as an ECS task (node dist/worker.js --run=check).
    If a real queue (SQS) is ever needed, enqueuing sits behind a RunQueue port,
    so only that adapter changes.
  - CI doesn't change. It's still backend/, with one image.

  Alternatives I rejected:
  - A separate collector/ package with its own package.json: domain types and
    entities would be duplicated or need a shared package, and ci.yml and the
    Dockerfiles would grow a third service.
  - pg-boss (a Postgres-backed job queue library): a reasonable choice, but it's
    a library and its own schema for something a single table we need anyway
    already covers.
  - Redis with BullMQ: extra infrastructure, as explained above.

  Do you agree: two entry points, one image, Runs table as the queue with SKIP 
  LOCKED, and a heartbeat for collector health? If so, I'll record it as an ADR,
  because it's architectural and someone will eventually suggest "just use
  BullMQ".

  Q18a: Who decides that a company is ambiguous at import?

  there's no curated file any more.

  Option: Rules only
  How it decides: Flag it if the name (ignoring a "formerly" part) is a single
  common English word or a person's first name (from a bundled word list), or
  is 3 characters or fewer (Ro, MST, Kini)
  Weakness: Misses names that are rare words but common in news ("Groq"?
  "Glean"?
  "Lemonade"), and flags harmless ones
  ────────────────────────────────────────
  Option: Ollama triage once at import (my recommendation)
  How it decides: The collector asks the model one question per company: "Would
  a
  news search for this exact name return many articles about unrelated things?"
   It returns { ambiguous, reason }, flagging  on any doubt. The rules above
  are applied too: a company  flagged by either goes to Needs review.
  Weakness: 258 extra LLM calls once (~10 minutes). The LLM could miss one, but
  that's caught later (see below).
  ────────────────────────────────────────
  Option: Probe search
  How it decides: Search the bare name, classify 10 results, and flag it if more

  than 30% are irrelevant
  Weakness: Most accurate, but ~2,500 LLM calls before anything starts

  This is consistent with ADR-003's rejected option. That rejection was about
  the LLM inventing descriptions that steer decisions silently. Here the LLM
  only raises a flag that a person then resolves, and it fails safe: a wrong
  flag costs a review, it doesn't produce wrong data.

  Safety net: the dashboard surfaces companies whose Candidates have a high 
  relevance rejection rate, which is the signal that an "unambiguous" company
  was actually ambiguous. One click moves it to Needs review.

  Q18b: Removing a company, and what "re-classify" covers

  - Remove: I'd recommend deactivating, not deleting. A deactivated company is
    excluded from Runs and the dashboard, and its Mentions are kept. Hard delete
    with history would be a separate, explicit action. Or do you want plain
    delete?
  - Re-process: editing search terms means the existing Candidates came from the
    old query, so re-classifying them isn't enough. I'd make it "Re-process 
    company": delete that company's Candidates and Mentions, then queue a
    Backfill limited to that one company. That's a fresh search and fresh
    classification, it reuses existing code, and it never alerts, because it's a
    Backfill. Saving a review on a "Needs review" company offers the same
    action. Does that match what you meant by "remove history after
    re-classify"?
