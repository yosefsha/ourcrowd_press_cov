The News Source returns **candidates**. Searching `"Harvey"` gives you Harvey Weinstein and Hurricane Harvey. `"Wave"` and `"Ro"` are worse. The question splits into two parts:

**(a) Where does the disambiguating context come from?** The seed list is names only. I recommend we keep `ourcrowd_companies.txt` as the source of truth for *who* is tracked, and add a curated `companies.json` next to it that enriches each entry with optional `aliases` (including the "formerly X" names), `domain`, a one-line `description`/sector, and `searchTerms`. **(b) Who makes the final call?** I recommend that Ollama decides relevance in the **same call** as sentiment. The prompt gets the company's name, aliases and description plus the article title and snippet. It returns `{ relevant: boolean, sentiment, reason }`. An irrelevant item is **kept but marked rejected**, not dropped. That gives an audit trail for the "how did you validate quality" section of the README. It also stops the daily job from re-classifying the same irrelevant article every day.

- **Candidate**: any item a News Source returns for a Tracked Company.
- **Mention**: a candidate the classifier confirmed is about that Tracked Company. Only Mentions appear on the dashboard, count toward the "last mentioned" status, and trigger alerts.

### Assistant [2026-10-07T07:49:32.924Z]
Yes. The `/api` proxy is what makes it work cleanly.

**Why it works:** the browser only ever talks to the frontend's origin, say `http://localhost:8080`. When the backend replies with `Set-Cookie` through the proxy, the browser stores the cookie for that origin, because it can't tell a proxy is involved. Every later `/api/...` request is same-origin and same-site, so a `SameSite=Strict` cookie is sent. The Vite dev proxy behaves the same way.

**Settings to get right:**
- **Don't set a `Domain` attribute, and use `Path=/`.** The cookie is then scoped to exactly the host the browser sees. If `Domain` were set to the backend's own hostname, the browser would reject the cookie.
- **The proxy must pass `Set-Cookie` through unchanged.** Both nginx and Vite's proxy do this by default. Just don't add cookie-rewriting directives.
- **Use `HttpOnly` always, and `Secure` whenever the site is served over https.** Chrome and Firefox treat `http://localhost` as secure, so `Secure` cookies work there. Older Safari versions don't, so a local run over plain http needs `Secure` controlled by config, with a production default of on.
- **Nest needs `app.set('trust proxy', 1)`.** It then reads `X-Forwarded-Proto` and `X-Forwarded-For` from the proxy and correctly detects https.
- **`SameSite=Strict` mostly closes off cross-site request forgery (CSRF)**, but it isn't a complete defence on its own. I'd also reject state-changing requests (`POST /checks`, Backfill, acknowledging a digest) whose `Origin` header doesn't match. That's one small guard.

(Without a proxy it would still technically work. `localhost:5173` and `localhost:8000` count as the same *site*, because ports don't matter for SameSite. But you'd need CORS with credentials, and that falls apart as soon as the frontend and backend are on different domains. The proxy avoids all of that.)

### Q14: How do runs behave: scheduling, overlapping runs and failures?

A Backfill and a Daily Check are both a **Run**. Here's what I propose for how they behave:

**(a) Scheduling.** A cron inside the backend (`@nestjs/schedule`), **daily at 07:00 Asia/Jerusalem**, configurable through `DAILY_CHECK_CRON` and `TZ`, so the digest is waiting at the start of the day.
- **Catching up:** a laptop is often asleep at 07:00. When the backend starts, if the last successful Daily Check is more than 24 hours old, it runs one immediately.
- **"Since the previous run"** = from the start of the last *successful* Daily Check minus 1 day of overlap. The overlap costs nothing, because duplicates are dropped and already-classified Articles aren't classified again, and it catches Articles Google surfaced late.

**(b) Only one Run at a time.** A Backfill and a Daily Check never overlap. They'd duplicate work and compete for Ollama. A lock in the database (at most one Run with status `running`) enforces this, and starting another returns **409 Conflict** with "Backfill in progress, 112/258". The dashboard greys out the buttons while a Run is going.

**(c) Failures.**
- **Fetching fails for one company:** record the error against that company and **carry on** with the rest. The Run ends as `completed_with_errors` and the operations panel lists which companies failed.
- **Ollama fails:** after **5 consecutive** classification failures, Ollama is treated as down and the Run stops as `failed`. Fetched Candidates are **stored unclassified** and picked up by the next Run, because classification is a separate step that can be retried.
- **Crash or restart mid-Run:** on startup, any Run still marked `running` is changed to `interrupted`. Starting again resumes it, because work already done is skipped.

**(d) One correction to "New Mention".** Take an Article fetched in Monday's run that couldn't be classified because Ollama was down, then classified as relevant on Tuesday. Under "first seen" it would never alert. The definition becomes **"first *confirmed as a Mention* in this Daily Check, and published within the last 7 days"**. Stated that way, failures can't swallow alerts.

### Q16: How do we separate the collector from the API server?

**Proposal: one backend codebase with two entry points, built into the same image and run as separate processes.**

```
backend/src/
  main.ts            → API server: HTTP only. Never fetches news or calls Ollama.
  worker.ts          → Collector: a Nest app with no HTTP. Runs Backfills and Daily Checks, owns the cron.
  coverage/ runs/ alerts/ ...   shared domain modules; each entry point imports only what it needs
```
- In `docker-compose.yml` the same image is used twice: `api` runs `node dist/main.js`, and `collector` runs `node dist/worker.js`.
- The API module graph **never imports** the NewsSource or classifier modules. A lint rule enforces that boundary, so the separation can't quietly erode.

**How they communicate: through Postgres, using the Runs table as the queue.**
1. The dashboard calls `POST /api/runs {type: "backfill", until, companies}`. The API **inserts a Run with status `queued`** and returns 202 Accepted. The one-Run rule becomes "at most one Run that is `queued` or `running`", enforced by a partial unique index, and a conflict returns 409.
2. The collector checks for queued Runs every few seconds. It claims one with `SELECT … FOR UPDATE SKIP LOCKED`, runs it, and writes progress to the Run row.
3. The dashboard keeps polling the API, which reads progress from that row.
4. The cron inside the collector does the same thing: it inserts a queued Daily Check.

**Why this approach:**
- **No new infrastructure.** We already need a Runs table for the lock, progress and history, so making it the queue costs almost nothing. The repo rules say not to add a service CI doesn't need. Redis with BullMQ would mean a Redis container plus CI changes for a queue that only ever holds one job.
- **Each process fails on its own.** If Ollama is down, the collector fails while the API keeps serving the dashboard. That also refines ADR-007: **only the collector** refuses to start without Ollama. The collector writes a **heartbeat** row with its Ollama health, and the dashboard shows "Collector offline" or "Ollama unreachable" instead of an API error.
- **The production path is clear.** The collector becomes its own ECS service, or EventBridge can launch it as an ECS task (`node dist/worker.js --run=check`). If a real queue (SQS) is ever needed, enqueuing sits behind a `RunQueue` port, so only that adapter changes.
- **CI doesn't change.** It's still `backend/`, with one image.

**Alternatives I rejected:**
- **A separate `collector/` package** with its own `package.json`: domain types and entities would be duplicated or need a shared package, and `ci.yml` and the Dockerfiles would grow a third service.
- **pg-boss** (a Postgres-backed job queue library): a reasonable choice, but it's a library and its own schema for something a single table we need anyway already covers.
- **Redis with BullMQ:** extra infrastructure, as explained above.

Do you agree: two entry points, one image, Runs table as the queue with `SKIP LOCKED`, and a heartbeat for collector health? If so, I'll record it as an ADR, because it's architectural and someone will eventually suggest "just use BullMQ".

1. **Its output is gitignored.** It writes to `compact-transcript-export.log` at the repo root, and that file is in `.gitignore`, so it would never be committed.
2. **It appends a full copy every time.** The transcript file keeps the whole session even after compaction, so every compaction plus the session end appends *another complete copy*. A long implementation session would produce the same conversation 3–5 times over in one file.
3. **The hooks are registered only in `.claude/settings.local.json`.** Your global git ignore excludes that file, so it's never committed and **doesn't exist in new worktrees**. Any session you start inside a `.claude/worktrees/...` directory wouldn't export anything.
4. **A cosmetic bug:** a session-end export is labelled `PreCompact export | trigger=unknown`.

**Proposed fix (small):**
- **Write one file per session to `docs/ai-prompts/<date>-<session-id>.md`, overwriting it each time.** Each compaction or session end then rewrites the complete, up-to-date transcript, with no duplicates, in a committed folder.
- **Always write into the primary checkout**, found with `git rev-parse --git-common-dir`, even when the session runs in a worktree. Every transcript then ends up in one place on `main`.
- **Move the two hook registrations to a committed `.claude/settings.json`** and remove them from `settings.local.json`, so they apply in every checkout and worktree.
- Fix the header so it shows the actual event (PreCompact or SessionEnd) and its reason.

**The one remaining manual step is committing.** A hook can write the file, but it can't safely commit to `main` on its own.
